# Muse for Android Auto — how Muse interacts with and uses this app

Muse for Android Auto is the Android Auto media app that gives
Jonathan eyes-free controls for a Muse voice session while driving:
its playback buttons are repurposed as the voice session's controls
(mic button starts/hangs up, Play/Pause mute and unmute his mic).
Project: `~/workspace/muse-android-auto/` (app in `auto-app/`;
repo `jonathancruzate/muse-android-auto`). The deep record is
`auto-app/README.md` — a recreation-grade changelog per release.

This skill ships with the app (Jonathan's standing rule, 2026-11-03:
every APK we build carries a skill teaching Muse how to interact
with and use it). The in-repo copy is
`~/workspace/muse-android-auto/SKILL.md`; the installed copy is
`~/workspace/custom-skills/local-muse-android-auto/SKILL.md`. They
are the same document — update both in the same handling, always.

## The facts that shape everything

- **Media is the only door.** A Muse *voice* app cannot exist in
  Android Auto: Google's calling/messaging car categories are
  closed/testing-only, and the Muse app itself declares no car
  support at all (REA-verified, `REA-FINDINGS.md`). Media is the one
  Auto category a sideloaded app may use — so this app is a media
  app whose transport controls ARE the product. Full route record:
  `ROUTE-COMPARISON.md`.
- **There is no intent into a Muse voice session.** The one voice
  deeplink, `hatch://voice`, is scoped ALL_FAMILY and enforced by
  Meta's TrustedCaller check — a dead end for any third-party app,
  by cryptographic design (REA method-level evidence). The only
  ungated external surface is `ACTION_ASSIST` into
  `com.facebook.aura/.main.AuraMainActivity`, which opens Muse's
  composer; this app's accessibility service then taps Muse's own
  voice button to make it a live session. No app can reach into
  Muse's session — this app is a control surface, not the call.
- **Current identity:** package
  `com.jonathancruzate.metamuseandroidauto`, display name "Muse
  for Android Auto". History: package was
  `com.jonathancruzate.musedrive` (display name "Muse Drive")
  through v2.3.x, then `…museandroidauto` in the unreleased
  v2.4.0, then the current metamuse family name in v2.4.1/v2.5.0.
  Display name renamed in v2.2.2; the feature's name is **"Muse
  Voice Mode"** (capital V, capital M) since v2.5.3.
- **Version source of truth:** `VERSION_CODE` / `VERSION_NAME` at
  the top of `auto-app/build.sh`, mirrored in the header of
  `auto-app/README.md`. Current: **v2.5.3, versionCode 14** (built
  2026-11-02) — display-name capitalization + bundled album art
  (Jonathan's profile photo) over v2.5.2's behavior.
- **Signing:** one certificate since v1 (SHA-256 prefix
  `314b8616…`); keystore `auto-app/keystore/musedrive.keystore`,
  alias `musedrive`, password file alongside it (0600). Same
  package + same cert = upgrades install in place. A package
  rename breaks that (see install lane below).

## What the app is (components)

- `DriveMediaService` — `androidx.media.MediaBrowserServiceCompat`
  + `MediaSessionCompat` (since v2.2.0; framework
  `MediaBrowserService` before that did not enumerate into the
  Auto launcher). Manifest carries the
  `com.google.android.gms.car.application` meta-data →
  `res/xml/automotive_app_desc.xml` declaring `<uses name="media"/>`.
  One playable item, **"Muse Voice Mode"** — a silent loop
  (`res/raw/silence.wav`, generated by build.sh).
- The car controls (verified against the code; README v2.5.1/2.5.2):
  - **Microphone button** (custom action "Talk to Muse") =
    **the voice toggle.** No session live → start: arm the
    session, fire ACTION_ASSIST, accessibility service taps
    Muse's voice button (view-id candidates incl.
    `hatch_voice_button`, then text/description; retries ~7 s).
    Session live → hang up (same end-call path as Stop).
  - **Play / Pause = his microphone only** (once a session runs):
    Play = `AudioManager.setMicrophoneMute(false)`, Pause =
    `setMicrophoneMute(true)`. They never start or end a session.
  - **Mute button** (custom action "Mute") = the same mic mute as
    Pause in one tap. It mutes HIS mic, never Muse's speaker.
  - **Stop / custom action "Hang up"** = end the session: the
    accessibility service's end-call hunt (view-id candidates
    incl. `end_voice_button`, then text/description), fallback
    Back → Home.
- `DriveAccessibilityService` — does the voice-button and end-call
  taps, and filters volume keys **only while a session is armed**:
  hold Vol DOWN = mute, hold Vol UP = unmute, hold BOTH = hang up.
  Short presses still change volume. Needs a one-time enable in
  Android Settings (per package — see install lane).
- `SessionState` — the armed flag is persisted to
  SharedPreferences `muse_drive_session` on every change and
  restored at startup by the service, accessibility service, and
  MainActivity, so the mic toggle stays truthful across process
  restarts.
- `WakeActivity` (v2.5.2) — screen-off trampoline: Talk/Hang up
  check `screenReady()` first; if the screen is off or locked,
  a wake lock + this `showWhenLocked`/`turnScreenOn` activity
  runs `requestDismissKeyguard`, and only after dismissal do
  the start/end taps run.
- `DriveReceiver` — exported receiver for the app's own broadcast
  actions `com.jonathancruzate.metamuseandroidauto.TALK / .MUTE /
  .UNMUTE / .END` (constants in `DriveActions.PKG`). These route
  between the app's own surfaces: the phone media notification
  (Talk/Mute/Hang up actions), MainActivity, and the MacroDroid
  macros in `macros/` (the `.MUTE`/`.UNMUTE`/`.END` macros carry
  matching IntentReceivedTriggers; the Talk macro uses
  ACTION_ASSIST). Since v2 the macros are a fallback lane, not
  the mechanism — mute/unmute/end run in-app.
- `MainActivity` — phone-side test panel firing the same actions,
  plus setup instructions and the CrashLog panel (below).
- `CrashLog` (v2.3.1) — a default uncaught-exception handler (and
  the guarded paths) record traces to the app-private
  `last_crash.txt`; MainActivity displays it with a Clear button.
  This is the crash-evidence lane: it captured the v2.3.2 root
  cause on-device.

## Build lane (raw build — the guards are the point)

- Build: `cd ~/workspace/muse-android-auto/auto-app && ./build.sh`.
  Raw javac/d8/aapt2 flow, **no Gradle, no emulator**. Toolchain:
  the meta-muse-widget SDK used read-only (build-tools 35.0.0,
  platform android-35) + Temurin JDK 21 from the local-rea tools.
  minSdk 29, targetSdk 35. Output:
  `Muse-Android-Auto-<version>.apk`, signed and apksigner-verified
  by the script. (v2.1.0 was also built on the VPS at
  `muse@167.233.41.12:~/muse-android-auto` with the box's SDK;
  the local read-only SDK is the documented default.)
- build.sh fetches pinned AndroidX artifacts from Google Maven
  into `libs/` if absent (media 1.7.0, core 1.13.1,
  versionedparcelable 1.1.1, lifecycle-runtime 2.6.2,
  interpolator 1.0.0, core-runtime 2.2.0 as AARs → classes.jar;
  annotation 1.8.2, collection 1.2.0, lifecycle-common 2.6.2,
  core-common 2.2.0, concurrent-futures 1.1.0 as JARs).
- **Guard 1 — empty-library fetch guard:** the build FAILS if any
  runtime library contains 0 `.class` files (annotation jar
  exempt — compile-only, never resolved at runtime).
- **Guard 2 — dex completeness guard:** the build FAILS if the
  finished dex references any androidx class it does not define
  (exempt: `androidx.annotation`, and library `R$*` resource
  stubs for library-internal layouts this app never inflates).
- Why they exist (v2.3.2 root cause, proven by CrashLog trace):
  androidx libraries that went Kotlin Multiplatform ship a bare
  `.jar` that is a METADATA jar (`.knm` files, zero classes); a
  raw `curl` does not follow Gradle's module-metadata redirects
  to the `-android` variants, so d8 silently dexed nothing and
  v2.2.0–v2.3.1 shipped referencing `androidx.collection.ArrayMap`
  without defining it — `NoClassDefFoundError` in
  `MediaBrowserServiceCompat.<init>`, before any app code ran.
  **Never remove or weaken either guard, and never fetch a bare
  jar for a KMP-gone androidx artifact**: pin the pre-KMP plain-jar
  versions (collection 1.2.0, lifecycle-common 2.6.2 — also the
  versions media 1.7.0 / core 1.13.1 declare in their POMs) or
  fetch the `-android`/AAR variant and dex its classes.jar.

## Install / upgrade lane

- Same package, same cert → install over the top; nothing else
  needed. The phone may lag versions if a delivered APK goes
  uninstalled — confirm what's actually installed before assuming
  the phone runs the latest build.
- **Package rename = fresh install, three follow-ups** (done for
  v2.4.0 and v2.4.1/v2.5.0; do all three or the app half-works):
  uninstall the old package and install fresh; **re-enable the
  accessibility service** for the renamed app in Android Settings
  (grants are per-package and do not carry over); **re-import the
  three macros** (`.MUTE`/`.UNMUTE`/`.END` action strings move
  with the package; regenerate via `macros/build_macros.py`).
- Phone-side setup checklist (Jonathan's hands, parked — never
  while driving; README v2.2.1): Android Auto → Developer
  settings → **Unknown sources ON** (required for any sideloaded
  Auto app to appear); Customize launcher → Muse for Android
  Auto checked; Settings → Apps → Muse for Android Auto →
  Battery → **Unrestricted** + add to Never sleeping apps (One UI
  sleeping apps drop out of the Auto launcher); open the app once
  on the phone, then reconnect to the car.

## Verification (what the repo actually documents)

- Build-side, every release: `apksigner verify` (cert
  `314b8616…`), `aapt2 dump badging` (package, versionCode,
  versionName, label), and DEX string/dexdump checks on the
  *shipped* APK (feature strings present, classes defined, zero
  old-name strings after a rename). The README's per-release
  sections record each run's results, APK size, and SHA-256.
- On-device: MainActivity's status line + working media
  notification show the media service is alive; the CrashLog
  panel is the verdict for crashes — if a build "keeps crashing,"
  get a screenshot of that panel before theorizing.
- In-car behavior is verified by Jonathan's parked tests (the
  checklist lives in `auto-app/README.md`). An adb/dumpsys
  verification lane is **not** established for this project —
  the README (v2.3.1) records the adb/logcat lane as
  retired/unreliable — so treat any dumpsys/media-session read
  procedure as unverified until a live run is recorded.

## When Muse reaches for this

- Jonathan is driving (or about to) and wants to talk to Muse
  hands-free: this app is the start/mute/hang-up surface — mic
  button toggles, Play/Pause or the volume-key holds mute, and
  in a live call he can also just say "mute" / "hang up" to Muse
  (voice self-command; unmute by voice is impossible — a muted
  mic delivers nothing — so unmute is always Vol UP long-press
  or Play).
- "The app crashed / won't open / disappeared from the car":
  work the recorded failure families first — CrashLog panel
  screenshot (a constructor/build defect looks exactly like an
  app bug), Unknown sources toggled off by an AA update,
  Customize launcher unchecked, One UI put the app to sleep.
- Any change to session controls, macros, or the build: this
  skill + the README changelog get updated in the same handling.

## Guardrails / regression rules

- **Never bypass the two build guards** (above) — a green build
  that skipped them is how the ArrayMap defect shipped four
  releases in a row.
- **Never chase a crash with untested hardening.** v2.2.1 and
  v2.3.1 shipped theories on top of an unproven diagnosis; the
  CrashLog trace settled it in minutes. Evidence first: CrashLog
  screenshot or it didn't happen.
- **The mic toggle state must stay persisted** (`muse_drive_session`).
  An in-process-only `armed` flag regresses the v2.5.2 fix: after
  a restart, the next mic press would re-start a session instead
  of hanging up.
- **Secure lock screen limit, stated plainly:** with a PIN /
  pattern / password / biometric lock, a screen-off mic press
  wakes the phone and shows Android's unlock prompt; the tap
  lands only after he authenticates. No app can dismiss a secure
  keyguard silently — never promise full screen-off operation on
  a locked phone. The hands-free workaround is Extend Unlock
  (Smart Lock) with the car's Bluetooth as a trusted device.
- **Never design around a Muse deeplink or Auto category that
  REA closed** (`hatch://voice`, calling/messaging templates).
  If a future Muse build changes the surface, re-run the REA
  pass and update `REA-FINDINGS.md` before building on it.
- Names: the feature is "Muse Voice Mode"; tooling, filenames,
  and identifiers say Muse, never Claude (the macro files were
  renamed for exactly this).
- Every build/change upstreams in the same handling: source push
  to `jonathancruzate/muse-android-auto` + GitHub Release
  (Latest, asset SHA verified against the build) + README
  changelog section + this skill (both copies) if the procedure
  changed.
